# Sacred Gold — mappings
#
# pureHD.exe v2.0.2.118, 32-bit, ImageBase 0x00400000.
# NOTE: pureHD.exe is itself a community wrapper/mod (it ships with pHD.dll),
# not the stock Sacred.exe.  Every address here is tied to THIS build.
# RVA = VA - 0x00400000.  Frida uses RVA (`baseAddress.add(rva)`), Ghidra/CE
# use VA.  Both are given because mixing them up silently produces a hook that
# never fires (see CLAUDE.md, "A silently dead hook is usually a wrong RVA").
#
# Append-only in spirit: add rows as they are confirmed, correct rows that turn
# out wrong, and never delete a row without saying why in the notes column.
#
# CONF column:  confirmed = observed live (hook fired / value matched the UI)
#               static    = read from the disassembly, not yet seen at runtime
#               suspect   = plausible, contradicted or untested
#
# Export tags: mappings.json is BUILT from this file by mappings.generator.py.
# A row Coderpack uses carries a tag at the start of its notes column:
#     [key=hpDamage]         -> exported as rva.hpDamage (or va.* for a global)
#     [key=hpDamage hooked]  -> and the agent attaches to it, so hooksafe.py
#                               checks the site for a trampoline hazard
# A row without a tag is documentation only.  Keys are unique across the file;
# two rows for the same address (both spellings of commitStats, say) may carry
# at most one key between them.  Never hand-edit mappings.json.
#
# Calling conventions: thiscall = ECX is `this`, stack args, callee cleans.
#   In Frida, `this` is the FIRST declared argument:
#     new NativeFunction(addr, 'int', ['pointer'], { abi: 'thiscall' })
#   cdecl (`mscdecl` in Frida) = all args on the stack, caller cleans.

# Combat arts: CORRECTED.  The "32-byte record with the level at +0x18" from
# the earlier session was a misattribution: that record belongs to the world
# object refresh vector (see refreshWorldObjectRecords), where +0x18 is a tick
# counter that happens to increase while playing.  What is actually confirmed
# now, read out of the game's own tooltips:
#
#   * combat arts are addressed by SLOT, and the slot argument the UI passes is
#     a byte offset stepping by 16, so the levels live in an array of 16-byte
#     elements, one per art.
#   * the Daemon has 12 slots.  Names and levels observed live:
#
#     slot  offset  name                             level (at the time of reading)
#        0    0x00  Dread                            13
#        1    0x10  Blazing Disc                     10
#        2    0x20  Abysmal Choir                     3
#        3    0x30  Call of Death                     5
#        4    0x40  Tentacles                        13
#        5    0x50  Infernal Power                    4
#        6    0x60  Hell Sphere                       5
#        7    0x70  Battle Daemon (Assail)           10
#        8    0x80  Energy Daemon (Charged Bolts)     ?
#        9    0x90  Fire Daemon (Wall of Fire)        9
#       10    0xA0  Poison Daemon (Poison Ring)       9
#       11    0xB0  Soaring Daemon (Descent)          8
#
# The storage was then found by watchpointing the cache and following the code
# that refills it.  There are TWO arrays:
#
#   1. a display cache of 16-byte elements (level at +0x00, art id at +0x02),
#      rewritten from the real store roughly every 15 ms, writing a level
#      there is visibly undone and never reaches the UI;
#   2. the authoritative array of 22-byte records, whose base was captured as
#      EBP at +0x180E1B.  The UI level is computed as base + bonus:
#
#          movzx cx, byte [ebp + idx*22 + 6]   ; base level      (+0x180E1B)
#          mov   al,  byte [ebp + idx*22 + 7]  ; bonus from gear (+0x180E0F)
#          add   ecx, eax                       ; what the tooltip prints
#
#      record layout (22 bytes):
#          +0x00  dword  1 or 2   (aspect group?)
#          +0x04  byte   art id   (0x3C..0x4E)
#          +0x05  byte   aspect   (0x00 for the first group, 0x04 for the second)
#          +0x04 and +0x05 are ONE word, the global art id the item modifiers and combos use:
#          art id + aspect * 256.  Live 2026-09-26 on a Vampiress, all 24 records resolved to a
#          named special move: (254, 3) 1022 Turn into Vampire, (50, 4) 1074 Claws of Death,
#          (11, 4) 1035 Bats.  The Daemon's (0x49, 4) is 1097 Battle Daemon.  The art level
#          lookup at 0x00580D80 compares this word with the id it is asked for.
#          +0x06  byte   BASE LEVEL   <- writing here sticks and shows in the UI
#          +0x07  byte   gear bonus
#          +0x0A  float  per-art value (regeneration?)
#          +0x0E  float  1.0
#
#      Confirmed live: after investing one rune each, Dread went 13 -> 14 and
#      Abysmal Choir 3 -> 4 in this array.
#
#      Slot order here is NOT the UI order, so identify an art by the id byte:
#          0x3C Blazing Disc      0x3F Infernal Power   0x40 Hell Sphere
#          0x41 Tentacles         0x42 Abysmal Choir    0x43 Dread
#          0x46 Soaring Daemon    0x49 Battle Daemon    0x4A Fire Daemon
#          0x4B Poison Daemon     0x4C Energy Daemon    0x3E Call of Death
#      (ids 0x44, 0x4D, 0x4E also appear in the array but not on the CA screen.)
#
#   The array's owner is the sheet: [sheet+0x102] is the vector's begin and
#   [sheet+0x106] its end (the rune path reads `mov ecx, [esi+0x102]`), and the
#   rune write is +0x1822AB (row above).  Both were open questions here once.
